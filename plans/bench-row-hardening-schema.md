# bench-row-hardening-schema — one header migration, five columns, three files (#4 #5)

You are phase `schema` of the `bench-row-hardening` plan. You widen all three
bench result headers **once**, in a single commit, adding the five-column
shared tail; teach every reader to tolerate the resulting mixed-width files;
and make the runners emit the new values. This is the hardest ordering
constraint in the workstream: two separate widenings would produce three row
widths in one file and two cross-era boundaries.

## Locked decisions (do NOT re-litigate)

See `plans/bench-row-hardening.md` and `docs/bench-hardening-spec.md`. Summary:

- **Shared tail, this exact order: `status date sha vsurv vtotal`.** `status`
  leads because it gates whether any other field means anything.
- `results-verify.tsv` gets `status date sha` **only** — no `vsurv`/`vtotal`.
  It *is* the verifier probe; its `verdict` column already carries the survivor
  signal, and a permanently-empty column trains readers to skim past emptiness.
- **Widen line 1 by hand. Do NOT backfill the 385 historical rows.** No reader
  requires uniform width, and backfilling asserts "no verify data" for runs
  whose data still exists in `bench/logs/*.err`. The invariant is
  `NF <= header NF`, not equality.
- **Empty cells are the empty string.** Not `-` — that is already live in
  bigdiff's `bugs` column meaning "zero known bugs matched"
  (`bench/score_bigdiff.py:122`). Not `NA` — one edit from a numeric column.
- **`vsurv`/`vtotal` are EMPTY, not `0`, when verification did not run.** An
  all-refuted run is `exit=0` with `vtotal=N`; a genuinely clean run is
  `exit=0` with `vtotal` empty. Defaulting them to 0 destroys the exact
  distinction #4 was filed to create.
- **New columns append at the END only, never insert.**
  `bench/rescore_bigdiff.py:33-34` maps header names to positions; an insert
  silently shifts every stored score.
- `date` is `date +%F` written **per row at append time** (a batch straddling
  midnight must not stamp every row with the start date). `sha` is computed
  **once per batch**, from phase `snapshot`'s frozen copy.
- Bundled here: the atomic-write fix for `bench/rescore_bigdiff.py:97`, because
  this phase already edits that file.

## Failure modes to watch

- **Anchoring the verify sed at `^verify:`.** It matches nothing, on every run,
  because the line is prefixed. The symptom is empty verify columns — which
  looks exactly like a non-verify run. This is the single most likely silent
  bug in the phase, and the end-to-end test against the real `review.sh` is
  what catches it.
- **Defaulting `vsurv`/`vtotal` to 0.** Collapses "zero findings survived" into
  "verification did not run" and destroys #4's whole purpose.
- **Hoisting `date` out of the row loop** for efficiency. A long batch then
  stamps every row with the start date.
- **Adding `date` to the rescore owner key.** A legitimately rescored row keeps
  its original date; keying on it would make every rescore look like a new row.
- **Widening a header without widening the rows the same commit writes.** The
  reverse direction — narrow header, wide rows — silently DROPS the new fields
  on read with no error at all, which is worse than a raise.
- **Touching a data row.** The three `.tsv` diffs must be one line each. If
  `git diff` shows more, something reformatted the file.
